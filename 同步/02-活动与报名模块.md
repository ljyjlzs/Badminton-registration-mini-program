# 02-活动与报名模块

> 覆盖云函数：`create-activity`、`join-activity`（扩展：level/固定搭档/候补/代报）、`cancel-registration` + `handle-cancel-request`、`get-rules`/`init-rules`、`get-activity-detail`、`update-user-*`。
> 目标：与 Java `ActivityController` / `RegistrationServiceImpl` / `RulesServiceImpl` 行为一致。
> **关键修正**：水平 `level` 是数字 1–10；候补判定 = `有效人数 ≥ maxPlayers`；取消逻辑看 `applyStatus` 而非比赛是否开赛。

## 2.1 create-activity（创建活动，对齐 ActivityServiceImpl.createActivity）
**入参** `{ name, time(yyyy-MM-dd HH:mm:ss), location, type, province, city, district, latitude?, longitude?, maxPlayers?, playersPerCourt?(仅 court-doubles) }`（province/city/district 必填；无 `desc`/`minPlayers` 入参，`minPlayers` 由后端按 type 计算）
- `type`：非 {singles/doubles/fixed-doubles/court-doubles} 之一 → 默认 `doubles`。
- `time` 必须晚于当前，否则 `BusinessException("活动时间必须是未来的时间")`。
- `minPlayers`：`singles=3`，其他 `4`（后端强制）。
- **非 court-doubles**：`maxPlayers` 默认 8，`clamp[minPlayers, 100]`（越界报错“报名人数上限不能低于 N 人”/“不能超过 100 人”）。
- **court-doubles**：读 `playersPerCourt`（默认 4，且 `≥4`，否则“按场地双打的每场人数至少 4 人”）；创建时即 `courtCount=1`、`maxPlayers=playersPerCourt`，并自动调 `court-config` 建 1 个场地（`场地A`）。后续加场用 08 `court-add`。
- 落库 `activities`：`status='registering'`、`currentPlayers=0`、`organizerId=userId`。
- **文本安全校验（`msgSecCheck`）后端不内置，由云函数侧对 name/desc 调用 `cloud.security.msgSecCheck`**。
- 返回 `{ activityId }`。

## 2.2 join-activity（报名）
**入参** `{ activityId, nickname, avatar, level(1-10), partnerId?, agent?(代报), partnerNickname?, ... }`
**逻辑（Java doJoinActivity / doWaitlistJoin）**
1. 活动必须 `status='registering'`，否则拒绝。
2. `currentCount = countValidRegistrations(activityId)`（`applyStatus='active'` 且未 approved 取消）。
3. **若 `currentCount >= maxPlayers`** → 走候补（`waiting`）；否则 `active`。
4. **fixed-doubles 且带 partnerId**：校验搭档已有效报名且未被他人绑定；双向绑定 `partnerId`（两人互指）。
5. 代报（agent）：可帮他人报名，`agentUserId=openid`，可创建 proxy 用户（昵称报名）；代报固搭同样双向绑定。
6. 重复报名校验；`level` 缺省 5；无候补时 `applyStatus='active'`。
7. 候补写 `waitlistOrder = max+1`。
- 返回 `{ registrationId, applyStatus, isWaiting }`

## 2.3 cancel-registration（取消）
**逻辑（Java cancelRegistrationInternal）— 看 applyStatus，不看比赛状态**
- `applyStatus='waiting'`（候补）：直接 `cancelStatus='approved'`，解绑搭档，立即生效。
- `applyStatus='active'`：置 `cancelStatus='pending'`，**需组织者审批**（见 2.4）。不下线、不释放名额直到批准。
- 已有 `pending` 申请则拒绝重复提交。

## 2.4 handle-cancel-request（组织者审批取消）
- `action='approve'`：解绑搭档 → `cancelStatus='approved'` → `currentPlayers-1` → **补位** `promoteWaitlist`（固搭/代报组需空 2 位才整组补）。
- `action='reject'`：`cancelStatus='rejected'`。
- 仅 `activity.creatorOpenid === openid` 可审批。

## 2.5 名额/上限
- `updateMaxPlayers`：minPlayers ≤ maxPlayers ≤ 100；maxPlayers ≥ currentPlayers；改大时触发 `promoteWaitlist`。
- 冲突检测（可选 MVP）：报名时若用户在 ±3 小时内已有其他活动报名，返回冲突提示（`checkConflict`）。

## 2.6 get-rules / init-rules
- `get-rules`：读 `rules(type='rules')`，无则返回 01 附录默认三套规则。
- `init-rules`：把 01 附录默认规则写入 `rules`（幂等：存在则更新）。

## 2.7 get-activity-detail
返回 `activity` + 当前用户 `registration`(applyStatus/cancelStatus) + `stats{activeCount, waitingCount, maxPlayers, minPlayers, currentPlayers, type, courtCount, playersPerCourt}` + `matchesSummary{当前/下一场/已结束数/总数}` + `album{title, note}`。

## 2.8 状态机与权限
- 活动 `status`：`registering→grouping→playing→finished`。
- 组织者操作校验 `activity.creatorOpenid === openid`。
- 代报人可管理自己代报的报名（取消/改搭档）。
