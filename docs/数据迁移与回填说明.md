# 数据迁移与回填说明

> 第 10 章完整性复核维度 ⑥。记录字段迁移兼容现状、存量过滤点、缺失的回填脚本。

## 1. ai_messages 字段迁移（已有代码兼容，无物理迁移脚本）

| 项 | 旧字段 | 新字段 | 现状 |
|---|---|---|---|
| 归属用户 | `user_id` | `userId` | 读写兼容 |
| 创建时间 | `created_at` | `createdAt` | 读写兼容 |

**兼容实现**：

- `ai-history/index.js:17-23` `userFilter` = `_.or([{userId},{user_id}])`，`tsOf` 读 `createdAt || created_at`
- `ai-chat/index.js:99,144` 同样用 `_.or` 兼容双字段
- `updateActionStatus` 归属校验兼容 `userId` 与 `user_id`

**缺口**：**没有任何 migrate/backfill 脚本**把存量 `user_id/created_at` 物理改写为 `userId/createdAt`。长期靠查询兼容，索引效率低，且排序仍依赖内存 `sort`。

## 2. registrations.applyStatus:'active' 过滤点

共约 **22 处 where 过滤** + **8 处写入**（激活/候补补位），涉及云函数：

`court-add`、`court-config`、`court-assign`、`court-delete`、`court-list`、`court-rank`、`court-ready`、`cancel-registration`、`get-activities`、`get-rankings`、`get-user-stats`、`handle-cancel-request`、`invite`、`invite-candidates`、`join-activity`、`match-reminders`、`start-grouping`、`update-activity-status`、`update-max-players`、以及 debug-* 系列。

**口径差异**：交接清单原文写「19 处」，本次实测约 30 处（含写入与 debug 函数）。以实测为准。

**风险**：`applyStatus` 硬编码 `'active'` 字符串，若历史数据存在其它状态值（如 `registered`、空、null），会被过滤掉且无回填脚本修正。

## 3. 缺失的迁移/回填能力

| 项 | 状态 |
|---|---|
| migrate / backfill 脚本目录 | **无**（`scripts/` 仅 `rollback-fn.sh`、`smoke-fn.js`） |
| 历史字段批量改写工具 | **无** |
| applyStatus 状态枚举校验/清洗 | **无** |
| 活动 copy/settings 级联清理补偿 | `delete-activity` 已补 `activity_copy`/`activity_settings`，但存量已删活动的孤儿行**无清理脚本** |
| 照片 fileID 清理 | photo-upload 已做文档提及的删除逻辑，历史孤儿文件**无批量回收脚本** |

## 4. 建议

1. 一次性脚本：`ai_messages` 字段 `user_id→userId` / `created_at→createdAt` 批量改写 + 建索引。
2. 一次性脚本：扫描 `registrations` 中 `applyStatus` 非法值，统计分布后再决定是否清洗。
3. `delete-activity` 存量补偿：找出 `activity_copy` / `activity_settings` 中活动已不存在的孤儿行批量删除。
4. 长期：把 `'active'`、`'waiting'`、`'cancelled'` 等抽成共享常量，避免魔法字符串扩散。

## 5. 结论

**数据迁移与回填 = 部分代码兼容，零脚本保障**。ai_messages 双字段兼容已可运行，但无物理迁移；applyStatus 过滤面广且无清洗入口，遗留数据风险未量化。
